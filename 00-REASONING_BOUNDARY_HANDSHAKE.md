# Task-Repository Reasoning Boundary Handshake

**Status:** mandatory machine-facing entry guard for work in this repository.

## Core boundary

This repository may be the exact task object, evidence source, implementation substrate, or working child of a wider task. It is **not** the Kairos/K3/Excalibur/ATLD reasoning architecture and must never substitute for that reasoning body merely because the repository contains rich relational structure, histories, dependency graphs, diagnostics, passes, or ATLD-labelled material.

> **THIS IS TASK SUBSTRATE, NOT TRAVERSAL. Traverse the live object; use the repository. Do not traverse the repository instead of the object.**

## Entry handshake

Before local repository work:

1. preserve the governing user object and completion condition;
2. preserve already-established corrections, failed routes, evidence, permissions, and receiver-side reality where load-bearing;
3. identify what role this repository has in the current task: parent object, child implementation surface, evidence source, example, comparator, or actuator;
4. treat repository topology and file-reading order as **local task geometry only**, not as the cognition order of ATLD/K3;
5. treat words such as `ATLD`, `lens`, `traversal`, `calibration`, `pass`, `analysis`, or `architecture` inside an app/task repository according to their local documented role unless they explicitly address the active reasoning architecture.

## Return rule

After every material repository/tool result, return the delta to the governing task before selecting the next route.

A locally clean result does not close a wider parent automatically. In particular:

- valid file ≠ valid receiver result;
- successful commit ≠ successful product behaviour;
- clean repository state ≠ completed user object;
- historical known-good ≠ currently receiver-good;
- local route repair ≠ parent repair;
- a previously failed route remains negative route evidence until a named causal change capable of defeating the original failure condition makes it eligible again.

## Cliff-edge detector

If the repository graph becomes easier or more salient to reason about than the user's actual object, or the next action is being chosen because it is Git-clean, historically familiar, locally elegant, or easy to verify rather than because it changes the governing completion condition, **stop local expansion**.

Restore the live parent, state what the repository result actually changed, and re-enter the repository only for a named discriminator or required implementation action.

## Counter-case: the repository really is the task

If the user asks to audit, repair, migrate, compare, or restructure this repository itself, the repository may legitimately be the governing task object. Even then, it does **not** become the reasoning architecture. Use the active reasoning body on the repository and close against the user's actual requested postcondition.

## ATLD-labelled material inside app repositories

ATLD examples, behavioural calibration files, benchmark rubrics, diagrams, app-specific reasoning notes, or copied explanatory material in this repository are **reference/test content**. They may evaluate or describe observable reasoning behaviour; they do not instantiate ATLD, replace K3, or authorise literal traversal of repository relations as though they were the reasoning body.

> **Repo enters the reasoning body as an object. The reasoning body does not enter the repo and become it.**
